    Technical field guide

    UNDER THE HOOD — MUMBAI NETWORK GARDEN

    This game lets you explore how connected networks work by building a simulated network with other players. Here is what powers the experience, and how it relates to real peer-to-peer networking.

    A

    How This Game Actually Works

    Implemented systems you can observe in the shared world.

    ↔ Live multiplayer and WebSockets USED IN THIS GAME

    The browser opens a same-origin WebSocket in apps/web/src/main.ts. The Node server in apps/server/src/app.ts accepts connections with the ws package, sends a snapshot first, then broadcasts batched delta events such as node.joined, link.created, outage.applied, and round.scored.

    That keeps players synchronized without refreshing. WebSockets are the transport used here; they are not libp2p connections.

    ◉ Player identity and presence USED IN THIS GAME

    The server assigns an application node ID and stores a session token. apps/server/src/view.ts derives player views, including joinedAt and online/offline presence from connected sessions. Reconnecting restores the application node when its token is valid.

    This ID is generated by the game server. It is not a cryptographic libp2p Peer ID and the app does not create a libp2p identity.

    ⌁ Connection requests and acceptance USED IN THIS GAME

    Selecting a node sends request_link. The target receives link_request and can accept or decline with respond_link. The server rechecks phase, node status, duplicate links, degree caps, and token rules before the engine creates a link.

    A pending request is stored separately and rendered as a dashed indicator. Only an accepted request produces link.created and an active logical edge. No browser-to-browser transport is opened.

    ● Nodes, edges, and topology USED IN THIS GAME

    Nodes are players; accepted links are graph edges. The authoritative graph lives in the engine state and is projected into NodeView and LinkView. apps/web/src/render.ts draws the current positions and edge geometry on a Canvas 2D surface.

    Dragging changes a node's coordinates through movement messages. It does not create or delete links automatically; distance is visual, not a connection rule.

    ➤ Packet Run and route finding SIMULATED

    The server's activeRoute() in apps/server/src/app.ts uses breadth-first search (BFS) across uncut links whose endpoints are active. It selects the first and last node in the current order as the mission endpoints, then sends the valid route in packetMission.

    apps/web/src/main.ts animates a dot along that route. If no route exists the mission is blocked or fails. This is a gameplay visualization, not a transmitted network packet or libp2p stream.

    ◎ Outages, reachability, and resilience USED IN THIS GAME

    packages/engine/src/outage.ts implements Hub strike (A), Cable cut (B), and Regional blackout (C), subject to the configured caps. Disabled nodes and cut links become inactive in the authoritative graph; recovery restores them at Results.

    Connectivity uses active nodes and active links. The score considers the largest connected component, articulation points (single points whose removal can split that component), and repair speed. Alternative paths improve survival, but this is graph simulation, not transport-level recovery.

    ◷ Game phases and scoring USED IN THIS GAME

    The engine advances through Growing/Build, Warning, Outage/Repair, and Results using configured timers. During Repair, packages/engine/src/scoring.ts calculates connectivity C, redundancy B, and speed S, then rounds the configured weighted result once with exact arithmetic.

    The server emits round.scored; the HUD shows the latest score and health trend. Seeding lines below five active nodes run build-only cycles and are not scored.

    B

    The Real libp2p Concepts Behind It

    Useful comparisons, with the implementation boundary stated plainly.

    Peer identity ANALOGY

    What it is: A libp2p Peer ID is derived from a peer's cryptographic public key. How real libp2p uses it: it identifies the peer during secure connection setup.

    Connection to this game: the server's player/node ID identifies a participant. Important difference: it is an application ID, not a libp2p key or Peer ID.

    Peer discovery NOT IMPLEMENTED

    What it is: mechanisms that find peers and usable addresses, such as a DHT or rendezvous service. How real libp2p uses it: discovery supplies candidates before dialing.

    Connection to this game: the player list helps you find nodes. Important difference: it comes from server snapshots; no libp2p discovery or addresses are exchanged.

    Dialing and connection establishment ANALOGY

    What it is: an outgoing attempt to establish a peer connection; JavaScript libp2p applications may use libp2p.dial(peerId). Connection to this game: Request Connection models intent and consent.

    Important difference: request_link is application-level WebSocket messaging. It does not call libp2p or create a transport connection.

    Connections, streams, and protocols NOT IMPLEMENTED

    What it is: a connection joins peers; a stream is a channel over it; a protocol defines how application messages are structured. Connection to this game: an accepted edge illustrates a relationship.

    Important difference: the game has no libp2p connection, stream, or negotiated protocol. Its messages are JSON over the game's WebSocket protocol.

    Publish/Subscribe NOT IMPLEMENTED

    What it is: a PubSub system such as GossipSub forwards messages to subscribed peers. Connection to this game: many clients may receive the same server broadcast.

    Important difference: broadcasts come from the authoritative WebSocket server; this app does not use GossipSub or another libp2p PubSub protocol.

    Relays and NAT traversal EDUCATIONAL ONLY

    What it is: relays can forward traffic when direct paths fail, while hole punching can help peers establish a direct path through NAT devices.

    Connection to this game: alternate graph paths are a useful analogy. Important difference: no relay, hole punching, or NAT traversal is implemented here.

    Resilience and alternative paths GRAPH ANALOGY

    What it is: redundant graph routes can preserve reachability when a node or link fails. Connection to this game: outage simulation, connected components, articulation points, and repair scoring make that visible.

    Important difference: this measures a simulated graph. It does not represent automatic libp2p reconnection or routing recovery.
